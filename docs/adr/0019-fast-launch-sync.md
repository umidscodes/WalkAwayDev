# Fast launch: the gh-broker keeps main current, the launch reads it locally

Date: 2026-11-08. Status: built, not run on the owner's mac. Owner decisions of 2026-11-08: the gh-broker refreshes each repo every 30 s; the refresh gets its own read-only token; a repo with no launch for 7 days drops out of the refresh; the first launch of a repo keeps the full sync; the agent's clones follow the gh-broker's copy in the background (item 8).

Changed on 2026-11-09 by `0020-state-based-branch-cleanup.md`: the refresh also ends merged branches. It mints a token that writes only to delete a branch whose recorded commit is in main; otherwise decision 2 holds.

So the sync was about half of the launch. It cost four steps in series, and two of them reached GitHub: `gh repo view` for the default branch (`defaultBranch`, `host/gh-broker/server.ts`, before this change) and a fetch into the bare repo (`refreshMain`, `host/gh-broker/server.ts`). Then a bundle of the full branch history (`handleSync`, `host/gh-broker/server.ts`) and the import in the clone (`importSync`, `host/gh-broker/client.ts`) ran on local disk. The config loop started about 60 processes, one `rm` and one `cp` per name.

The 30 skill description compression calls fail at each start (429 from the `smol` model), but omp starts them after the TUI is up and does not wait for them at exit (omp 18.18.1 bundle: `deferSkillDescriptionCompression`, `startSkillDescriptionCompression`, `void sd.waitForPending()`). They are not part of the wait.

## Decision

1. **The gh-broker refreshes main on a timer.** Every 30 s, for each repo synced in the last 7 days, the gh-broker runs `git ls-remote --symref <url> HEAD` (`refreshRepos` and `refreshMain`, `host/gh-broker/server.ts`). It returns the default branch and its commit in one round trip (agent run, 2026-11-08: `ref: refs/heads/main	HEAD`, then the commit). The branch name goes through the same check as before (`parseRemoteHead` with `isDefaultBranchName`, `host/gh-broker/protocol.ts`). When the commit differs from the copy's ref, the gh-broker fetches. A check counts as good only when the listing and any fetch it needed both succeeded; the gh-broker records the start time of each good check per repo, in memory. A repo with no sync for 7 days drops out; its next launch adds it back. A broker restart forgets every repo, so the first sync after it asks GitHub. Each check, from the timer or inside a sync, stops after 20 s from its start in the queue (`CHECK_TIMEOUT_MS`, or `checkTimeoutMs` in the config), so a stalled GitHub call holds the repo's queue for at most that long. A failed timer check is logged, never thrown.
2. **The timer uses a read-only token.** The gh-broker mints it with `permissions: {"contents": "read"}` and caches it apart from the token that pushes and merges (`TokenScope`, `createAppTokens`, `host/gh-broker/github-app.ts`). Before, one token per repo had all of the app's permissions, because the request named only the repo, and GitHub gives such a token "all of the permissions that were granted to the app" (https://docs.github.com/en/rest/apps/apps, "Create an installation access token for an app", read 2026-11-08). The other verbs keep the app token. A sync that must ask GitHub uses the read-only token too.
3. **Only a launch sync reads the gh-broker's copy.** `agent-start` runs `gh-broker sync <repo> --cached` (`agent-start:72`). A plain `gh-broker sync`, as an agent runs it before a rebase (`../../AGENTS.md`, "Work a change"), always asks GitHub first, so it gets the main of that moment; it is still faster than before, with one GitHub call and no full history. After a merge through the gh-broker, the copy no longer counts as current, so the next launch asks GitHub. Either way the client sends the commits of its `refs/remotes/origin/*` refs, without `origin/pr/*`, as `have` (`originHeads`, `host/gh-broker/client.ts`). The gh-broker accepts at most 16 full 40-hex commits, and `cached` only as `true` (`MAX_SYNC_HAVES`, `validateRequest`, `host/gh-broker/protocol.ts`). For a `--cached` sync within 40 s of its last good check, it answers from local disk: no bundle when a known `have` already contains the branch commit, else a bundle of `refs/heads/<branch>` minus the known `have` commits, else the full bundle. If the last check is older or missing, as after a broker restart, a wake from sleep, or a merge, it first runs the check of step 1 once. Every reply names the branch and its commit; the client sets `origin/<branch>` to that commit and refuses when the result differs. When an import fails, the client asks once more with no `have` and imports the full bundle. It prints the same line as before, `origin/<branch> is now <commit>`, so `agent-start:78`, the setup wizard, and the tests that read it do not change.
4. **The first launch of a repo keeps the full sync.** A new clone has no `origin/*` ref (`agent-start:63-69`), so the client sends an empty `have` and gets the full bundle, as before.
5. **One queue per repo.** Every write to a repo's copy runs through one promise chain per repo: the timer check, a sync, `sync --pr`, and push (`inRepoQueue`, `host/gh-broker/server.ts`). The branch cleanup after a merge writes nothing in the copy, so it stays outside. Before, the gh-broker had no lock, queue, or mutex, so a timer fetch and a sync could move `refs/heads/main` at the same moment.
6. **The config copy is two commands.** `agent-start` deletes every name in `config-names` with one `rm`, then clones the staged names with one `cp -cR` (`agent-start:36-47`). `/Library/Underground` and `/Users` are on one APFS volume, so the clone copies no data; if it fails, the launch stops with `cp`'s error, because nothing hides it. The reset of the agent's own config at each start stays (`../THREAT-MODEL.md`, U6). A hash compare is not used: hashing both sides took 0.15 s and 0.19 s, longer than the clone (agent runs, 2026-11-08).
7. **The hash of the omp binary, the config copy, and the sync start together; omp starts only after all three.** `agent-start` runs the hash and the copy in background subshells (`agent-start:18-22,36-47`) while the sync runs, then waits for the hash as soon as the sync returns and for the copy before it starts omp (`:73`, `copied`, `:49-51`). The hash wait comes before any check of the sync's result, so a broken binary, which breaks the sync too because the client runs the same binary, reports the hash and not the gh-broker. The trade, chosen by the owner on 2026-11-08: the gh-broker client runs the binary before the check ends. Only root can change the binary (`0017-one-omp-binary-and-no-ug-folder.md`), and the client runs as the agent user with the gh-broker socket that each session has, so a bad binary gains nothing in that window that a session lacks [inference]. The session itself never starts on a bad binary. Agent runs of `agent-start --version` in one batch, 2026-11-08, 7 each: 0.17 s to 0.27 s in a repo against 0.31 s to 0.40 s for the order before; 0.15 s outside a repo. An earlier run that seemed to show no gain still ran the config copy before the sync.
8. **The agent's clones follow the gh-broker's copy in the background (owner decision, 2026-11-08).** Steps 1 to 3 kept the gh-broker's copy current, but not the agent's clone, so a launch from a clone that is behind still imported the new commits. Measured on 2026-11-08: `gh-broker sync --cached` in a copy of the agent's clone took 0.24 s to 0.38 s when behind and 0.11 s to 0.14 s when current (agent runs, 4 each); `time omp --version` took 0.99 s for the launch that caught the clone up and 0.43 s to 0.54 s for the next five (owner runs; the clone's reflog shows the import at that launch). Now the LaunchDaemon `com.underground.agent-refresh` runs `agent-refresh` every 30 s as `ugagent` under the pin (`host/agent/com.underground.agent-refresh.plist`). It runs `gh-broker sync <repo> --cached` in each clone in `~/work/<owner>/<repo>`, under the same `.git/ug-sync.lock` as a launch, and skips a clone that a launch holds (`lockf -t 0`). It skips a clone with no launch in the last 7 days, by the time of `.git/ug-launched`, which `agent-start` touches at each launch, so the 7-day rule of step 1 still holds. It runs git with hooks off, stops a sync after 20 s, and logs only failures to `~/logs/agent-refresh.log` (`host/agent/agent-refresh`). A launch waits at most 3 s for that lock; then it starts from the main that the clone has and says so on stderr (`busy`, `host/agent/agent-start`). `StartInterval` and not `WatchPaths` on a file that the gh-broker touches, because launchd calls `WatchPaths` "highly race-prone" (https://keith.github.io/xcode-man-pages/launchd.plist.5.html, read 2026-11-08), and a missed event would leave the clone behind with no sign. A run when main did not move costs one sync with no bundle, 0.16 s (agent run). Setup installs the job with `ug_ensure_service` (`host/bin/ug-agent-setup`). Expected gain: the 0.13 s to 0.24 s of a behind sync; the rest of the 0.99 s launch above is not explained [inference: a cold first run; not measured].

Expected result: a launch of about 1.1 s to 1.3 s, with the sync part at about 0.15 s, or about 0.35 s when the check of step 1 runs at launch. The sum includes the 0.13 s hash of the omp binary. [inference: the sum of the parts above; not run.]

Retest after setup (agent runs, 2026-11-08, `agent-start --version` with the agent config folder moved to a temp folder, 7 runs each): 0.45 s to 0.49 s in a repo, 0.27 s to 0.29 s outside a repo, before step 7; 0.31 s to 0.37 s and 0.16 s outside a repo after it. Parts: `gh-broker sync --cached` 0.12 s to 0.15 s, the hash 0.13 s, `cp -cR` of the staged names into an empty folder 0.07 s to 0.08 s (the delete before it was not timed again), `git checkout` 0.02 s, `omp --version` 0.02 s. The ssh login and the omp TUI start are not in these runs.

Full launch, owner run of 2026-11-08, `omp` in a repo, quit with `/exit` at once, against an agent-side watcher at about 10 ms: omp's first log line at 0.73 s after enter, the session worktree at 0.93 s, the worktree removed at 2.88 s, and the owner's shell back at 2.90 s. Nothing logs the prompt or the arrival of `/exit`, so the 1.9 s between the worktree and its removal holds the owner's reaction and omp's exit in unknown parts.

## Accepted risk

A launch within 30 s of a merge that the owner makes on GitHub starts from the old `main`, with the old `AGENTS.md` in the system prompt for that session. We accept it. It can be undone: CI runs on every pull request (`pull_request`, `.github/workflows/ci.yml`), GitHub refuses a merge with conflicts [inference: GitHub's default, not read today], and an agent syncs and rebases when its branch needs the current `main` (`../../AGENTS.md`, "Work a change"). The next launch after the next refresh gets the new rules.

## Rejected

- **A hook at the first turn that syncs and moves the worktree.** omp loads `AGENTS.md` into the system prompt at start, so the session keeps the old rules unless the hook rebuilds the prompt. It needs a second PR in the config repo, a guard against later turns and subagents, and a timeout for a failed sync. The owner chose the timer.
- **No sync at launch; the agent syncs first.** The same stale-rules gap, and a rule in `AGENTS.md` is a request, not a control.
- **A fetch after each session exits.** In `agent-start` it moves the wait to the exit (`start_omp` ends in `exit 0`, `agent-start:28`); in the background under sshd it can be killed. It also misses the owner's merges on GitHub.
- **A GitHub webhook.** It needs a public address or an outside relay that sees the repo's events.
- **A session started ahead of time.** Its `main` and config are stale before use, and it holds resources all day.

## Cost

GitHub: the check of step 1 is a git operation. "Git operations do not consume part of your API rate limit" (GitHub support, quoted in https://github.com/orgs/community/discussions/44515, read 2026-11-08; not an official doc). The read-only token adds about one token request per repo per hour, against at least 5,000 API requests per hour per installation and 2,000 token requests per hour per app (https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api, read 2026-11-08). CPU: about 0.09 s per check, so about 4 to 5 minutes a day per repo at one check every 30 s.

Code: `host/gh-broker/server.ts` (timer, check, local sync, queue), `host/gh-broker/github-app.ts` (read-only token), `host/gh-broker/protocol.ts` (`have`, `parseRemoteHead`, the reply with `head` and an optional bundle), `host/gh-broker/client.ts` (send `have`, import or set the ref, retry once), `host/agent/agent-start` (the copy). One PR. The owner merges it and runs `host/bin/ug-setup` once, which installs the client and restarts the gh-broker. A launch while setup runs can meet a new client and an old gh-broker; the old one ignores `have` and sends no `head`, so that one sync fails, and the next launch works.

Docs: `../SPEC.md`, "Session start"; `../THREAT-MODEL.md` (the agent user table: the new `have` input and this accepted risk).

## Checks

- Broker tests (`tests/broker/sync-pr.test.ts`): a second sync gets no bundle; a `--cached` sync within 40 s gets the copy, after 40 s the gh-broker asks GitHub and sends only the new commits; a plain sync asks GitHub even 1 s after a check; a refresh lets the next `--cached` sync skip GitHub; the refresh asks only with the read-only token and skips a repo with no sync for 7 days; a refresh and a sync at the same moment both succeed; an unknown `have` gets the full history; `have` refuses `--all`, `^<sha>`, a short sha, 17 shas, and a PR sync, and `cached` refuses anything but `true`. `tests/broker/server-failures.test.ts`: an unreadable default branch from GitHub fetches nothing; a hung `ls-remote` stops at the deadline for the refresh and for a sync, and the next sync answers; a refresh whose copy cannot be made resolves. `tests/broker/github-app.test.ts`: the read-only token request and its own cache. `tests/broker/flow.test.ts`: a sync after a merge (`gets the merged main`, `tests/broker/flow.test.ts`), and a `--cached` sync right after a merge gets the merged main; it passed in a scratch copy whose fake `gh` ran under the pinned omp's bun (agent runs, 2026-11-08); in the checkout it needs node, so CI runs it.
- Facts run with real git (agent run, 2026-11-08): a delta bundle imports into a clone that has the base; `git bundle create` refuses an empty bundle (`Refusing to create empty bundle`) and an unknown base (`bad object`); a clone without the base refuses the import (`Repository lacks these prerequisite commits`).
